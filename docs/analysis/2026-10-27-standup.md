## Summary

In practice the call was a two-person review: one teammate (the tester) went through the
user's depreciation report for 12 minutes, gave their own update for 4, then asked the user
about plans. The 2026-10-26 fixes held: **no answer fired for a teammate** (3 of 3 fired
questions were the user's), and the user's first name was recognized. What went wrong:

- **Most turns that were the user's got nothing.** Of 8 turns where the user was asked
  something, 3 got an answer. The biggest misses: whether the plan for the next report changes
  (should the roadmap dates move?), and a check that the migration ticket was still open. The
  pack had material for both. Cause: the group-call rule assumes several remote speakers who
  mostly talk to each other. Here there was one, and the detector turned down "you ... right?"
  checks that came seconds after the user had spoken.
- **The detector stalled for about 50 seconds** (13:46 to 14:36) while OpenAI was slow to
  first token: 10 decisions failed outright and 29 calls hedged, because the hedge and the
  retry go to the same model. No turn of the user's fell in that window, by luck. Earlier, the
  name-addressed "...right, [first name]?" took 2.8 s to decide (hedged), so the answer reached
  the screen 3.5 s after the question, when the user was already talking.
- **Commitments pile up.** The report stored 6 commitments, most of them steps of one task
  (fix the blank values, double-check the ranges, make the period mandatory, keep fixing).
  The post-call model never sees the open commitments, so it cannot skip or close them. The
  two broken ones from 10-26 ("the session date was not provided", a misheard report name)
  are still open. The next pack lists 8 open commitments.
- The conversation summary hit its 500-token cap again (7th call), and the pack as loaded
  was overwritten again after the call (fixes 6, 7 and 9 from 10-26 were not done).

Latency: fast first word at the client 3.3 s p50 and 3.5 s p95 on the two `respond`
questions, and 1.5 s on the status question, against 0.7 to 1.2 s; the detector and a slow
provider account for nearly all of it. One fast-pass first-token timeout, no STT drops, no
reconnects, two echo lines dropped. Cost about $0.21, **about $0.62 per live hour against the
$0.84 estimate**, with the detector at about 950 calls an hour and about 330 held fast passes
an hour (estimate: 250 and 20), as on 10-26.

## 3. Standup checks

**Addressee.** Precision 3 of 3 (10-26: 2 of 7). Recall 3 of 8, or 3 of 6 counting only
turns that needed more than a "no". Every miss came seconds after the user had spoken, in a
call with one remote voice. The detector prompt for standups says "Them is several people, and
most of what they say is to each other", and lets "you" count only "right after the user
spoke". On gpt-6-luna, that first sentence wins: a yes-or-no check on the user's own work
("you're still on X, right?") came back `none` each time. The 300-token detector window did
hold the user's preceding line in every case, so the text it needed was there.

**Content.** The pack was built at 00:51 UTC from the 10-26 log, 14 hours ahead; "yesterday"
was 10-26, a Monday, which is correct for a Tuesday. Answers cited real nodes (the branch
cleanup, the shared-library briefing, the planned code review) and invented nothing, except
that the fast pass of Q3 added "I'll pick that up after the depreciation work", a plan the
user had not stated. Q3's fast pass cited the broken 10-26 commitment. Prepared points were
not used (best similarity 0.53).

**Conversation memory.** Later answers used what the user had said: Q3's fast pass carried
"make the period mandatory" from 13:32, and Q1's deep pass raised the average-or-total
question that the tester asked a minute later. Summaries grew from 161 to 500 output tokens
over seven calls; **the last one ended at the 500-token cap**, so the newest notes in it were
probably cut. On gpt-6-luna there are no reasoning tokens, so this is the summary text itself
outgrowing its budget, not the reasoning headroom that the 10-26 analysis suspected.

**Post-call report.** The due date worked ("today" became 2026-10-27), and the commitments
read cleanly. But:

- 6 commitments, 4 of them steps of the same fix; the post-call request carries no open
  commitments, so nothing is merged with or closed against the 2 from 10-26.
- The two broken commitments from 10-26 stay open: only a work log's extraction can close a
  commitment, and today's log is not written yet.
- "Blockers" lists an order of work (finish depreciation before the next report; pass testing
  before migration), not something blocking the user.
- "Yesterday" says only that the user was busy, which is what was said: the user was never
  asked for yesterday's work.

## 5. Ranked issues

Ranked by effect on the user in a real standup.

### 1. Turns that are plainly the user's are missed in a small standup

- **Evidence:** 5 of 8 turns for the user showed nothing, among them the roadmap question
  (asked four ways over 30 s) and the migration check; all came within seconds of the user
  speaking, with one remote voice in the call (section 3).
- **Root cause:** the group-call rule tells the detector that "Them" is several people
  talking to each other. The model gets no signal about how recently the user spoke or whether
  the call is a back-and-forth, so it falls back on that premise. Yes-or-no checks about the
  user's own work fall between `respond` ("a check right after they spoke") and `none`.
- **Fix:** (a) The gateway gives the detector the turn-taking facts it now has to infer: how
  many seconds ago the user last spoke, and whether the recent lines alternate between Them
  and the user. (b) Replace the premise in the group rule: "you", "right?" or a question
  about the user's own work, coming within about 20 s of the user's last line or in a
  back-and-forth with them, is for the user. Name the case "you're still on X, right?" as
  `respond` or `standup_status`. (c) Add paraphrased cases of these misses, plus group
  counter-cases where "you" follows the user but is for someone else, to
  `evals/bench/group_standup.toml`. Later (not in this branch): Deepgram diarization on the
  "them" stream, so the gateway knows when there is only one remote speaker (needs a price
  check).
- **Expected gain:** most of the 5 misses become answers; the roadmap question in
  particular.
- **Risk:** false fires return in large standups when "you" right after the user is for
  someone else. Offline tests only check the prompt and the hint; the group bench measures it
  live (about 60 detector calls, under $0.01). Backend-only.

### 2. A slow provider stalls the detector, and named questions wait for it

- **Evidence:** 10 failed decisions and 29 hedges, mostly between 13:46 and 14:36. Q1, which
  ended in the user's first name, took 2.8 s to decide, and the answer showed at 3.5 s after
  the user had started answering.
- **Root cause:** the hedge and the retry both go to `openai:gpt-6-luna`, so a slow spell
  slows both. A failed decision counts as `none`. And even a question that ends by naming the
  user waits for the model.
- **Fix:** (a) A rule the gateway applies itself: in standups and meetings, an utterance
  that addresses the user by first name (the name at its start or end, or before a "?", not
  "check with [name]") releases the held fast pass at once as `respond`, and the detector
  can then only upgrade its type. The same rule decides when the detector fails. (b) Send the
  hedge to a different route: OpenAI's Priority tier for gpt-6-luna (`service_tier`), which
  adds 75% to a call of about $0.0001 and only on the 10% of calls that hedge, or Claude Haiku
  if you want a second provider (it needs an Anthropic key in Secret Manager; your call).
- **Expected gain:** a named question shows in about 1 s instead of 3.5 s; a provider slow
  spell no longer silences the detector for questions that name the user.
- **Risk:** (a) can fire on a vocative that is not for the user, for example a namesake; a
  later `none` from the detector cannot pull it back (the user dismisses it). (b) Priority
  is an untested latency claim; measured live later. Backend-only.

### 3. Commitments pile up and are never merged or closed

- **Evidence:** 6 new commitments, 4 of them one task; 8 open in the next pack, including the
  two broken ones from 10-26.
- **Root cause:** `postcall_request` gets no open commitments, and the standup prompt asks
  for "every commitment"; only a work log's extraction can close one.
- **Fix:** give the standup report the company's open commitments with short ids (as
  `worklog.extract` gets them). It returns only new commitments, steps of one task merged into
  one, at most 3, and `closed_commitments` for those the user said are done or replaced. These
  are closed with `closed_by` set to the session, so a rerun reopens them as the work log path
  does. Also tighten "Blockers": an order of work is not a blocker. Separately, and only with
  your OK: drop the two broken 10-26 commitments on Stage 0.
- **Expected gain:** the next pack shows the 2 or 3 commitments that matter.
- **Risk:** the model closes something that is still open. It shows on the post-call screen,
  and a work log can reopen it. Backend-only.

### 4. The conversation summary outgrows its cap

- **Evidence:** output grew 161 → 241 → 321 → 423 → 489 → 453 → 500, with 500 the cap.
- **Root cause:** the prompt allows up to about 355 words, which is the whole budget, and asks
  for no compression, so each call adds to the last; on a long call the end is cut.
- **Fix:** ask for at most about 60% of the budget, merging and dropping older detail first.
  Log the stop reason; on `max_tokens`, keep the previous summary and carry the lines over to
  the next call instead of storing a truncated one.
- **Expected gain:** later answers in a 30+ minute call keep the newest context. **Risk:**
  low; the summary carries less old detail. Backend-only.

### 5. The deep pass arrives after the user has answered

- **Evidence:** Q3's deep answer at 6.6 s (first token 4.6 s on gpt-6.1-sol). The user had
  answered at 0.4 s after the question.
- **Fix:** for `standup_status` and `respond`, which the pack and the fast pass cover, run
  the deep pass only on expand (`deep_pass_auto_types`). That saves about $0.007 per question
  and keeps the panel from changing while the user talks.
- **Expected gain:** a steadier panel, a little cost. **Risk:** detail moves behind a tap.
  Backend-only (a setting).

### 6. Not enough recorded to analyze a call

- **Evidence:** the pack as loaded overwritten twice; no keyterm count; no detector tokens
  (section 1).
- **Fix:** log at session start the pack id, `built_at`, memory version and keyterm count, and
  at session end the detector's call, hedge and failure counts with tokens.
- **Expected gain:** the next analysis needs no reconstruction. **Risk:** none. Backend-only.

### 7. The profile has no timezone or standup time

- **Evidence:** both the account's and the profile's settings are empty, so every "today" and
  due date is a UTC date, and the scheduler has no standup time to build a pack for.
- **Fix:** set them in the app's Settings for the profile (no code). Right today only because
  15:00 UTC falls on the same date in US time zones.

### 8. Detector and held-pass rates far above the cost estimate (as on 10-26)

- **Fix:** update the estimate in ARCHITECTURE.md for talk-heavy standups: about 950 detector
  calls and 330 held passes an hour. A doc change; the gating idea from 10-26 still stands
  before any Claude routing.

1 and 2 first: they decide whether the user gets help when it is their turn. Then 3 (what the
next standup starts from), then 4 and 6 (small and cheap), 5 if the panel churn bothers you,
and 8 as a doc change. Item 7 is a setting for you. Everything listed is backend-only; no new
