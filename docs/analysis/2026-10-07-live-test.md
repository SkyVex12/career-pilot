# Live test, 2026-10-07: latency and detection analysis

**Session:** `01a11850-1eab-7212-ae92-1c2f567518df`, started 2026-10-07 21:41:06 UTC, ended 21:48:49 (7 min 43 s). Interview mode, desktop app on Windows, Zoom, a teammate asking interview questions.

**Providers:** `COPILOT_LLM_PROVIDERS=openai` only. Detector and fast pass on `gpt-6-luna` (reasoning `none`), deep pass on `gpt-6.1-sol` (reasoning `low`), embeddings `text-embedding-3-large` at 1024 dimensions, first-token timeouts 3 s (fast) and 6 s (deep). STT: Deepgram.

**Transcript consent was off** for this session. Aurora holds no text, and this report quotes none. The analysis used the session's live event stream in Valkey (`sess:{sid}:events`, kept for 2 h for resume), read locally, and describes questions only by type and time.

## Summary

The first word took **2.7 s at p50 and 5.3 s at p95** (server side, automatic questions), against the 0.9 s / 1.5 s SLO. Almost none of that time is the model's first token. The time goes to steps that run one after another but were designed to overlap:

1. The fast pass waits for the detector on every question. The detector takes 1.2–1.7 s on OpenAI, so the speculative path never ran: 0 of 10 questions were sent as speculative.
2. On 3 of 8 automatic questions the detector ran twice in a row (once on the interim text, then again on the final), adding 1.3–2.1 s. These 3 questions are the p95.
3. Prepared answers never hit. The cause is the 0.85 similarity threshold, which is too high for `text-embedding-3-large`, not the embedding speed: the two questions with a prepared answer scored 0.74 and 0.64.

There were no errors, timeouts, fallbacks or reconnects.

## 5. Ranked issues

Issues are ranked by their effect on the first word the user sees. The four hypotheses from the brief are marked **H1–H4**.

### 1. The detector is on the critical path for every automatic question (H1: confirmed)

- **Evidence:** on every direct question, the fast pass starts within 20 ms of the detector returning, so the first word is `detector_ms + TTFT` (Q2: 1,233 + 796 → 2,046). The detector took 1,219–1,672 ms (p50 1,390), and 0 of 10 questions were speculative.
- **Root cause:** `TurnDetector._turn` awaits the detection before `begin_question`. The design assumed a Haiku detector that returns inside the 300 ms speculative window. A 1.3 s detector moves the whole answer back by 1.3 s.
- **Fix:** at `t0 + speculative_start_ms`, start the fast pass on the current text while the detector runs, and hold its deltas in the gateway. When the detector fires on the same text, release the buffer and stream on. When it does not fire, or the speaker continues, cancel the pass silently, with no `question.detected` sent and nothing shown. Skip utterances under 3 words (greetings and acknowledgements). Make it a setting, on by default, since it only costs money when the detector is slow.
- **Expected gain:** the first word becomes about `max(detector, 300 ms + TTFT)` instead of `detector + TTFT`: p50 from 2.7 s to about 1.6 s. OpenAI alone still misses 0.9 s; the floor is the detector, about 1.3 s.
- **Risk:** extra fast passes on non-questions: about 40 speech ends in this session × about $0.00012 cached on `gpt-6-luna`, so about $0.005 per session, or about $0.03 on Haiku. A held pass started on a cut-off interim is thrown away and restarted if the detector fires on different text (issue 2). Adds a state to `turn.py` and `answer.py`.

### 2. The final recheck runs the detector twice in a row (3 of 8 questions; this is the p95)

- **Evidence:** on Q1, Q3 and Q9, `turn_end_ms − detector_ms` = 2,046, 1,313 and 2,095 ms elapsed before the second detector call even started. Those three questions had first words of 5.3, 3.8 and 4.5 s.
- **Root cause:** the interim text at `t0` lacks the last words, often the object of the question and the question mark, so the detector correctly says "incomplete". Only after that call returns does the gateway wait for the final, and only then does it run the detector a second time. The STT final usually arrives while the first call is still running.
- **Fix:** when the STT final arrives during a pending turn and its text differs from the text being checked, start the detector (and, with fix 1, the held fast pass) on the final at once, alongside the first call, and act on the result for the newest text. The "no interim" path (Q7) is the same case, and the change removes its 328 ms wait too.
- **Expected gain:** −1.3 to −2.1 s on about 40% of automatic questions. p95 from 5.3 s to about 2.2 s.
- **Risk:** up to one extra detector call per turn (about $0.0001). Turn logic is the most delicate code in the gateway; the tests must cover interim-fires, final-fires and neither-fires.

### 3. The prepared-answer threshold is wrong for OpenAI embeddings (H2: refuted as stated; the real problem is calibration)

- **Evidence:** 0 hits. Offline, the two questions that have prepared answers scored 0.735 and 0.639 with margins of 0.40 and 0.21 over the runner-up. The gate is 0.85. The embedding (0.45–1.8 s) ran alongside the 1.2–1.7 s detector and was done in time on 7 of 8 automatic questions.
- **Root cause:** `prepared_answer_min_similarity` is one number for every embedding model. 0.85 suits Cohere v4; `text-embedding-3-large` scores paraphrases around 0.6–0.75.
- **Fix:** make the threshold depend on the embedding model (`COPILOT_PREPARED_MIN_SIMILARITY` per model id, with 0.85 for Cohere), and require a margin over the runner-up. Calibrate both with a paraphrase set built from the pack's 30 questions (positives) plus unrelated interview questions (negatives), checked in under `evals/`. The starting point is 0.60 with a 0.15 margin.
- **Expected gain:** 2 of 10 questions here (20%) would show prepared points as soon as the detector fires (about 1.2–1.6 s) with no fast-pass call. With fix 1 they would also arrive before the model's text.
- **Risk:** a false match shows points for a different question. The margin rule and the calibration set bound this, and the fast pass still runs for the deep context. Medium risk until the set exists.

### 4. Fixed 150 ms wait for the prepared match on forced and recheck questions (H2, the part that holds)

- **Evidence:** on Q6, Q8 and Q1 the fast pass started 157, 141 and 158 ms after the question began. That is `PREPARED_WAIT_S`, spent because the embedding had only just started.
- **Fix:** do not wait. Start the fast pass at once and let a prepared hit take over the slot if it arrives before the first model token. If the model's text is already streaming, the hit is dropped.
- **Expected gain:** −150 ms on forced questions and rechecks (3 of 10 here).
- **Risk:** low.

### 5. The first question of a session runs with a cold prompt cache

- **Evidence:** Q1 was the only answer with `cached_tokens = 0`: fast TTFT 1,562 ms against a p50 of 1,015. The same digest and pack had been used 4 h earlier. The gateway never sets `prompt_cache_retention`, so OpenAI's default in-memory retention applies (minutes, not the 24 h PR #6 mentions), and `ModelRouter.warm` only opens the connection.
- **Fix:** at session start, after the pack loads, send one fast-pass request with the session's real prefix and the smallest output limit, so the cache is primed before the first question. Fast pass only: the deep pass was not slower cold.
- **Expected gain:** about −0.5 s on the first question of each session.
- **Risk:** low. About $0.0006 per session on `gpt-6-luna` (about $0.007 as a Haiku cache write).

### 6. Waiting for the STT final (H4: minor on its own)

- **Evidence:** `final_wait_max_ms` (1,500 ms after the silence timer) was never reached. The wait costs time only in the no-interim path (Q7, about 328 ms) and inside rechecks.
- **Fix:** none separately; fix 2 removes both cases. The setting stays.

### 7. Anthropic and Bedrock clients drop idle connections after 5 s (H3: not exercised; confirmed in code)

- **Evidence:** this session used only OpenAI. In `providers.py` the Anthropic and Bedrock clients use the SDK default `httpx.Limits` (`keepalive_expiry = 5.0`), and `AnthropicProvider` has no `warm()`. On a Claude configuration, every question that follows more than 5 s of quiet pays a new TLS handshake.
- **Fix:** give them the same `Limits` as OpenAI (`openai_keepalive_s`, renamed to apply to all providers) and a `warm()` (a models list on the direct API).
- **Expected gain:** about 100–300 ms per question on Claude routes. Not measurable from this session.
- **Risk:** low.

### 8. Detection quality: 3 misses, 2 false fires

- **Evidence:** section 3.
- **Fix now:** log every detector decision (fields, latency, tokens and cost, never text) so the next test can explain misses. Add one line to the detector prompt: requests for an action are not questions that need an answer.
- **Later:** threshold and "incomplete but clearly a question" changes need the labeled corpus, not one call.
- **Risk:** the prompt change could lower recall; check it on the recorded fixtures.

### 9. Measurement gaps (needed to analyze the next test fully)

- Send the client's first-word time per question and pass to the gateway (new client message `latency.report`) and store it in `answers.latency_ms` as `client_first_word_ms`, together with the anchor.
- Add to `latency_ms`: `final_ms` (t0 to STT final), `fast_start_ms`, `prepared_ms` and `prepared_similarity`, and `expand_ms` (the deep pass after an expand counts from the tap).
- Keep `provider` and `fallback_attempt` in `latency_ms`.
- A gateway log file per run (`COPILOT_LOG_DIR`), with the session id on every line.
