# XRuby delegation from CoRuby

Implemented in the isolated `codex/db-redesign` checkout based on `ba8f3416b0cfba8627697a1445b5a5f19183e20b`. This is an owning-product integration: CoRuby authorizes and interprets its own recorded sources; HubRuby holds an encrypted account-private delegation and calls fixed endpoints. No live credentials, providers, migrations or deployments were used during implementation.

## Consent and authority

`COPILOT_XRUBY_OAUTH_ISSUER` is an exact HTTPS origin. The OAuth issuer is that origin plus `/v1/xruby/oauth`; the resource is the origin plus `/v1/xruby`. `COPILOT_XRUBY_OAUTH_CLIENTS` maps fixed client IDs to exact allowlisted callback URLs. These settings are independent of the existing MCP OAuth registry. Empty issuer/clients leave this integration unavailable. Loopback HTTP is accepted only in local/test/dev environments.

The consent page uses the existing email sign-in, then requires an explicit profile and, for company reads, an explicit company. It pages at 50 choices and identifies requested scopes. It does not match accounts by email or reuse broad application/MCP tokens. Authorization-code PKCE uses S256, a single-use 120-second code and exact client/redirect/resource binding. Callback `iss` identifies the independent issuer. Access tokens are opaque `xruby_` tokens whose server-side lookup keys are SHA256 hashes. Default lifetime is 1,200 seconds, configurable between 60 and 3,600 seconds. There is no refresh token; reconnect when the delegation expires. Each account can retain at most 20 active grants.

Read scopes are `xruby:interviews:read`, `xruby:work:read`, `xruby:retrospective:read`, and `xruby:sources:read`. Source retrieval additionally requires its source-kind scope. A separate optional `xruby:interviews:prepare` scope allows confirmed paid draft generation and requires interviews:read plus writable profile membership. Read-only consent never authorizes generation.

Every delegated request rechecks the exact live grant, active account, explicit profile membership and its authorization revision, active selected company, and the existing CareerOS-link requirement when configured. Membership revocation and regrant does not resurrect an old token. Profile overrides are rejected. Source reads check authorization again after their database phase; generation additionally fences reservation/publication/revocation through a persistent account lock. Consumer calls check connection metadata before and after a source operation. Revocation endpoints delete the remote token and fence any pending generation; old consumers cannot continue through their local cache.

`GET /v1/xruby/connection` adds current validated IANA `timezone` (UTC fallback), `server_time` in UTC, and live `capabilities.prepare_interview`. These are read under the same account/profile authorization transaction. The timezone is a mutable account setting, not a frozen consent field. For “last week”, HubRuby computes the last completed Monday-to-Monday interval from the owning server clock and timezone and verifies the timezone remains the same after the read. Other envelopes keep the immutable consent metadata shape.

## Factual reads

| Endpoint | Source and boundaries |
|---|---|
| `GET /v1/xruby/next-interview` | Earliest recorded future interview occurrence. Includes company, role, round and UTC start. Optional aware `as_of`. Calendar sync, cancellation and completion are not recorded by this source, so it does not claim them. |
| `GET /v1/xruby/current-work` | Active selected-company work-item/commitment memory. Explicit status, date precision, blockers and overdue calculation in account timezone. Priority/missed are not inferred. This is recorded memory, not an exhaustive work tracker. |
| `GET /v1/xruby/retrospective` | Current immutable saved work-log revisions and saved AI session feedback in a caller-selected 1–31-day window; start inclusive, end exclusive. User reports and generated feedback retain their distinct provenance. Feedback does not prove a mistake. |
| `GET /v1/xruby/interviews/{id}/preparation` | Deterministic checklist tied to an observed interview revision/hash. Returns source presence/hashes and current pairing metadata, not JD/resume bodies. No model, scheduling or queue action. |
| `GET /v1/xruby/sources/{kind}/{id}` | Current fixed source projection, only with exact `revision` and `expected_hash`. A changed source returns 409. Kinds: interview, interview_preparation, work_item, work_log, feedback. |

Pages contain at most 20 items and responses at most 128 KiB. Source routes use a 15-second application deadline and five-second statement timeouts. Opaque cursors bind the grant, query and page limit, expire within 300 seconds/the grant lifetime, and preserve `as_of`. Pagination is a live keyset, not a snapshot of the entire collection. Saved encrypted text is size-checked before retrieval; oversized retrospective sources are reported as omitted. Source citations bind product, exact profile/company, kind, UUID, revision and canonical JSON SHA256. The consumer uses fixed typed paths rather than following arbitrary remote citation URLs. Interview and preparation citations have company/employer null because their authority is the selected profile's application, not an inferred employment relationship.

The composite preparation projection includes occurrence metadata, saved JD hash, explicit/current paired resume identity/revision/content hash and exact encrypted text fingerprint, plus existing-pack presence. Existing-pack presence is not a claim that its cached content is current. Cancellation, interview completion and source timezone are explicitly unknown where the owning schema has no such fields.

## Confirmed generation

`POST /v1/xruby/interviews/{id}/preparation-requests` accepts `{revision, expected_hash}` from the **composite interview_preparation citation**, with a required stable `Idempotency-Key` of 1–128 characters. Revision must equal that composite hash. It returns HTTP 202 and an immutable request receipt. `GET /v1/xruby/preparation-requests/{request_id}` returns its current state. Both require the exact same unexpired prepare grant and current profile authority. A changed body/grant/interview/hash under the same account/key returns 409; repeat the same request after transport uncertainty rather than generating a new key.

States are `queued`, `leased`, `dispatched`, `succeeded`, `rejected`, `uncertain`. PostgreSQL commits the dispatch marker before the single model call. A crash, timeout or invalid response after dispatch is terminal uncertain. No old/new worker can reset that marker or issue a second provider call for the receipt. An expired lease can be reclaimed only before dispatch, with an increased generation; stale owners cannot dispatch or publish. The executor has a 90-second lease and 70-second operation deadline; dispatch requires at least 55 seconds left on both lease and grant. The model call holds no database transaction. Source/grant/lease checks run again before publication.

The first supported generation requires an **explicit application-to-resume pairing**, a current immutable extracted resume revision, and saved JD and resume text each at most 24 KiB UTF-8. Implicit “latest base resume” selection is refused because inserting a different base version cannot be safely frozen by locking the application row alone. The generated draft reuses the existing `SessionPack` serializer, bounded to 64 KiB, and is encrypted with the existing profile data-key mechanism. It is returned only while the exact source hash is still current. It is not automatically attached to an interview/live session, cached as the ordinary pack.build output, embedded, sent to anyone or scheduled. Coverage excludes memory stories and other unsupplied material. Generated language still requires human review.

Receipts expose `provider_dispatched`, scalar `usage`, `usage_status` (`measured`, `unknown`, or `not_dispatched`), and explicit false scheduling/session-attachment fields. A completed provider JSON response preserves observed token usage even if draft validation later fails. An unreadable/oversized/failed transport can leave usage unknown. A reservation is **not an invoice** and does not prove a provider charged money. Reservations and measured/unknown usage survive source/grant revocation; uncertain attempts are never automatically refunded or retried.

The direct provider adapter makes one fixed-origin OpenAI Responses HTTP request with strict JSON Schema output, `store=false`, no redirects, no tools and no SDK/router retry or fallback. It preserves the configured `COPILOT_OPENAI_PACK_MODEL` and optional existing pack reasoning setting. The configured model must support the requested Structured Outputs schema. Output is capped at 256–4,000 tokens (default 2,000), the response body at 64 KiB, HTTP timeout at 30 seconds and overall provider phase at 35 seconds. A model/provider failure does not switch to another provider. `store=false` disables response retrieval storage; it is not a claim of zero data retention. Reviewed against [Responses request format](https://developers.openai.com/api/reference/resources/responses/methods/create), [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses) and the [SDK retry contract](https://developers.openai.com/api/reference/python).

Generation requires all of the following; defaults remain off/zero:

- `COPILOT_XRUBY_PREPARATION_ENABLED=true` on every serving CoRuby instance.
- `COPILOT_XRUBY_PREPARATION_DAILY_LIMIT` between 1 and 20, per account per UTC day.
- `COPILOT_XRUBY_PREPARATION_GLOBAL_DAILY_LIMIT` between 1 and 10,000, across all accounts for the shared provider payer per UTC day.
- Existing `OPENAI_API_KEY` and `COPILOT_OPENAI_PACK_MODEL`; `OPENAI_BASE_URL` must be unset for this reviewed fixed-origin path.
- Optional `COPILOT_XRUBY_PREPARATION_MAX_OUTPUT_TOKENS` within the above bounds.

The two reservation ceilings are atomic persistent counters. Both are consumed once when a new request is accepted, including requests that later become rejected/uncertain; a key replay consumes neither. Choose ceilings from the real payer's spend policy and configured model pricing. Count and token limits do not enforce a dollar-denominated invoice ceiling. The executor initially runs one request at a time per enabled API process; throughput must be provisioned deliberately rather than assuming 100,000 monthly active users all generate simultaneously.

## Schema and rollout

Apply the owning product's existing migration process (`uv run copilot-migrate`) through `0037` on an explicitly selected restored rehearsal database first. `COPILOT_DATABASE_URL` is the migration credential; runtime uses restricted `COPILOT_API_DATABASE_URL`. Use the existing coordinated deployment/backup/rehearsal procedure in README; never point a rehearsal command at a production default.

`0036_xruby_delegated_reads.sql` adds three bounded-read indexes. `0037_xruby_preparation.sql` adds account-private request and budget tables plus a separate global payer counter, forced RLS, immutable dispatch guards, a bounded lease claim function, an account-bound budget reservation function and a source-lock-only helper. The helper allows locking immutable resume rows without granting the API UPDATE on those source tables. Generic app_worker/app_system/app_gateway receive neither ledger access nor these execution entrypoints. Normal API access is account-scoped; the reviewed claim function returns only bounded authority/lease identifiers, never source bodies, generated content or raw tokens. No schema is created at application startup. Enabling generation refuses missing migration objects, bypass/owner runtime roles and missing forced RLS.

Deploy the updated OAuth/revocation readers and migrations to every API instance before enabling delegation/prepare uniformly. Register only the exact HubRuby callback and resource. Reconnect to add the new prepare scope; an existing read-only connection does not gain it. User confirmation must remain separate from natural-language read planning.

For rollback, stop new confirmations, revoke affected grants, allow current dispatches to settle or mark themselves uncertain, then stop/drain the dedicated executor before disabling its feature flag. Do not revert migration checksums, delete receipts/budgets, reset a dispatched marker, move these operations into pack.build, or remint a key automatically to recover a timeout. Existing ordinary pack.build behavior is unchanged. Receipt/state/history remains in PostgreSQL; source deletion/changes invalidate retrieval. There is no new automatic retention or full account-erasure claim: a future explicit policy may remove encrypted result payloads while preserving the minimal dispatch/budget facts required to prevent paid replay.
